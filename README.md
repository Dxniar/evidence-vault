# Evidence Vault — версия для развёртывания

Flask-приложение для хранения цифровых доказательств: расследования, SHA-256, 2FA, роли и журнал действий. Метаданные и учётные записи хранятся в **Supabase PostgreSQL**, файлы — в **приватном Supabase Storage bucket**. Браузер обращается только к Flask; строка подключения и ключ Storage остаются на сервере.

Интерфейс поддерживает светлую и тёмную темы: кнопка «Тема» доступна на всех страницах, выбор сохраняется в браузере. При первом посещении используется системная тема. Короткие анимации отключаются при включённом уменьшении движения.

Для бесплатного учебного размещения подготовлены [инструкция Render](РАЗМЕЩЕНИЕ_RENDER.md) и `render.yaml`. Контейнер использует порт из переменной `PORT` или локальный `8080`.

## Роли

| Действие | Администратор | Следователь | Аудитор |
| --- | --- | --- | --- |
| Создавать пользователей, менять роли и блокировать доступ | Да | Нет | Нет |
| Просматривать дела и скачивать файлы | Все | Свои и назначенные | Все |
| Создавать дела, загружать доказательства | Все открытые дела | Свои открытые дела и назначенные с правом добавления | Нет |
| Проверять SHA-256 | Все дела, с обновлением ручного результата | Владелец/редактор — ручной результат; участник с правом просмотра — наблюдение | Все дела, без изменения ручного результата |
| Просматривать журнал | Все события | События доступных дел и собственные общие события | Все события |

## Рабочие процессы

Ответственный за дело и администратор назначают участников с правом просмотра или добавления материалов. Изменение доступа и сведений требует основания и сохраняется в истории. Закрытие блокирует добавление файлов и изменение состава; просмотр, выдача и проверка остаются доступны. Незавершённые передачи нужно принять или отменить до закрытия.

При загрузке можно указать источник, протокол, способ и дату получения. Известная исходная SHA-256 проверяется до сохранения; для такой проверки загружается один файл. Незаполненные сведения явно отмечаются в сводке. Существующим материалам не присваивается выдуманная история или первоначальный ответственный.

Передачу ответственности инициирует текущий ответственный; получатель должен иметь доступ к делу и подтвердить принятие. Повторное принятие блокируется, ответственный и событие меняются одной транзакцией. Назначение доступа и передача ответственности — разные действия.

Сводка по делу печатается из браузера. JSON-перечень содержит метаданные, SHA-256 и историю передач, без содержимого файлов и серверных ключей. Файлы скачиваются с префиксом их ID и безопасным именем, совпадающим с `export_name` перечня. Проверить скачанные материалы **без подключения к БД и без .env** можно после установки зависимостей:

```powershell
python operations.py --manifest case-1-manifest.json --files-dir ./exported-files
```

Совпадение SHA-256 не удостоверяет автора перечня или происхождение материала. Сводка не является подписанным процессуальным документом. Для печатного интерфейса даты показываются в UTC+05:00; настройка `DISPLAY_TIMEZONE_OFFSET_HOURS` меняет отображение. В БД и JSON даты остаются UTC.

## Контроль состояния и качества

`/healthz` проверяет процесс; `/readyz` выполняет настоящий запрос к PostgreSQL и проверяет приватный bucket. Ответы readiness кешируются отдельно в каждом процессе на 15 секунд, при отказе возвращается 503 без секретов. У ответа есть `X-Request-ID` для сопоставления с ошибками.

Новая миграция `e24b8f0a6c31_casework_and_custody.py` добавляет поля и таблицы без удаления существующих записей. PostgreSQL-триггеры блокируют UPDATE/DELETE событий и изменение исходной идентичности файла; ORM также защищает от случайных изменений. Владелец инфраструктуры способен отключить эти ограничения: они не заменяют независимый аудит или защищённое от удаления хранилище.

Файл `.github/workflows/checks.yml` подготавливает автоматические проверки Python/JavaScript, изолированные тесты и сборку Docker при подключении проекта к GitHub. Публикация репозитория и запуск GitHub Actions в этой работе не выполнялись.

Публичная регистрация закрыта. Первого администратора создают командой `bootstrap-admin`; затем он добавляет сотрудников через интерфейс. Есть два способа добавить сотрудника:

- **С начальным паролем.** Администратор задаёт почту, роль и начальный пароль. Сотрудник входит, подключает TOTP и обязательно меняет пароль до доступа к делам. Смена пароля завершает прежние сеансы.
- **По приглашению Google.** При настроенном OAuth администратор заранее задаёт почту Google и роль без выдачи пароля. Приглашение действует 7 дней. Сотрудник нажимает «Войти через Google» и выбирает именно приглашённый аккаунт. Администратор и аудитор дополнительно подключают или подтверждают TOTP; для следователя отдельный TOTP после Google не требуется. Постоянный идентификатор Google сохраняется в записи с ролью, заданной администратором. Администратор может продлить приглашение или отключить пользователя. Письма приложение не рассылает: сообщите сотруднику адрес приложения и приглашённую почту самостоятельно.

Уже существующие учётные записи после обновления сохраняются с действующими паролями и без принудительной смены. Пользователь, вошедший только через Google, может создать локальный пароль в профиле с **новым** кодом 2FA; до этого отключить Google нельзя.

## Вход через Google (лабораторная № 2)

Google используется как внешний поставщик личности по OpenID Connect. Supabase по-прежнему хранит пользователей и роли, но не выполняет вход через Google за Flask-приложение. Существующий пользователь с паролем сначала связывает Google в профиле, подтвердив пароль. Приглашённый администратором сотрудник может впервые войти через Google без пароля, но только с **заранее указанной подтверждённой почтой**, пока действует приглашение. В обоих случаях приложение сохраняет постоянный Google ID `sub`; одного совпадения почты для уже созданной учётной записи с паролем недостаточно. Открытой регистрации нет.

При каждом новом Google-входе и при привязке аккаунта приложение передаёт `prompt=select_account`: Google показывает выбор аккаунта даже при уже открытой Google-сессии. Следователь после подтверждения личности Google входит без отдельного локального TOTP; администратор и аудитор подтверждают TOTP Evidence Vault. Вход по почте и паролю для всех ролей требует TOTP. Для демонстрации повторного входа выйдите из Evidence Vault и снова нажмите «Войти через Google».

Google-вход следователя не означает, что приложение проверило второй фактор у Google: правила Google-аккаунта контролирует поставщик личности. Приложение хранит метод входа в подписанной сессии и повторно проверяет роль, привязку Google, активность и версию сеанса. Google-сессия следователя не даёт входа без TOTP после назначения ему роли администратора или аудитора. Новый следователь может дополнительно подключить TOTP в профиле, если нужен вход по паролю.

1. Откройте [Google Cloud Console](https://console.cloud.google.com/), создайте проект и настройте **Google Auth Platform → Branding** и **Audience**. Для проверки в режиме *Testing* добавьте используемые Google-адреса в список тестовых пользователей.
2. В **Google Auth Platform → Clients** создайте OAuth-клиент типа **Web application**. В **Authorized redirect URIs** укажите **точно** `http://localhost:8080/auth/google/callback` для запуска на своём ПК. Если позже появится домен с HTTPS, добавьте отдельный URI вида `https://vault.example.com/auth/google/callback`. Используйте в браузере тот же адрес хоста, который зарегистрирован в Google: `localhost` и `127.0.0.1` различаются.
3. В существующий `.env` добавьте `GOOGLE_OAUTH_CLIENT_ID` и `GOOGLE_OAUTH_CLIENT_SECRET` из созданного клиента. Храните секрет только на сервере. Если Google-вход не нужен, не задавайте обе переменные: кнопка входа будет скрыта. При одной заполненной переменной запуск намеренно останавливается с ошибкой настройки.
4. После замены файлов проекта выполните **новую миграцию до запуска новой версии**. Распакуйте содержимое `evidence-vault-prod` в уже существующую папку с `Dockerfile` и `compose.yaml`, без вложенной второй папки. Для уже настроенного проекта на Windows:

```bat
docker compose build
docker compose run --rm web flask --app app db upgrade
docker compose up -d
```

Не повторяйте `bootstrap-admin`: существующий администратор и пользователи сохраняются. Перед распаковкой сохраните свою `.env` и убедитесь, что она осталась на месте; архив `.env` не содержит. **В этом обновлении нужно заменить все файлы проекта**, включая `models.py`, `app.py`, шаблоны и каталог `migrations`: одного `app.py` недостаточно. Перед миграцией проверьте наличие `migrations/versions/c83f4e7a0d12_invited_google_users_and_password_rotation.py` и `migrations/versions/d91a3b6c8e20_integrity_observations.py`. Последняя миграция добавляет отдельные поля результата и времени наблюдения целостности; существующие записи сохраняются.

5. Для существующего пользователя: войдите паролем и TOTP → **Профиль → Подключить Google** → подтвердите текущий пароль, выберите Google-аккаунт с той же **подтверждённой** почтой. После этого выйдите и проверьте **Войти через Google**. Для нового сотрудника: администратор создаёт приглашение в **Пользователи → Пригласить через Google**, сотрудник нажимает **Войти через Google** и выбирает приглашённый аккаунт. Следователь сразу получает доступ; администратор и аудитор подключают или подтверждают TOTP. Роль при входе не меняется.

Если кнопки нет, проверьте обе переменные в `.env`, пересборку образа и `docker compose logs --tail=50 web`. При `redirect_uri_mismatch` проверьте точное совпадение URI в Google Cloud и адреса браузера. Если после нажатия «Подключить Google» остаётесь на странице профиля, проверьте сообщение вверху: «Неверный пароль» относится к паролю Evidence Vault, а не Google; браузеры на Chromium также требуют разрешить `https://accounts.google.com` в `form-action` политики страницы (в этой версии это настроено). `check-setup` проверяет Supabase, но не проверяет Google-клиент: для него нужен проход входа в браузере. Основа интеграции: [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) и [настройка веб-клиента Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server).

## Подготовка Supabase с нуля

1. Зарегистрируйтесь в [Supabase Dashboard](https://supabase.com/dashboard), создайте организацию при необходимости и нажмите **New project**. Выберите регион, задайте **пароль базы данных** и сохраните его в менеджере паролей. Дождитесь готовности проекта. Выделите отдельный проект для этого приложения.
2. В проекте откройте **Storage → New Bucket**. Имя: `evidence-private`; режим **Private** (`public=false`). Оставьте ограничения MIME пустыми, а лимит размера bucket — пустым либо **не меньше 16 МБ**. В **Storage Settings** убедитесь, что глобальный лимит загрузки тоже не меньше 16 МБ. Это необходимо для файлов Evidence Vault; браузер не получает прямого доступа к bucket.
3. В **Connect** скопируйте строку подключения PostgreSQL. Для постоянно работающего сервера с IPv4 выберите **Session pooler**, порт **5432**; при доступности IPv6 подходит Direct. Не составляйте имя сервера вручную. Вставьте пароль базы вместо `[YOUR-PASSWORD]`, URL-кодируя специальные символы (например, `@` → `%40`). Transaction pooler на 6543 для этого приложения не используйте.
4. В **Settings → API Keys → Secret keys** создайте или скопируйте серверный ключ `sb_secret_...`; отдельно скопируйте URL проекта вида `https://<project-ref>.supabase.co`. Ключ нужен только серверу. Старый JWT `service_role` также поддерживается через переменную `SUPABASE_SERVICE_ROLE_KEY`, если проект всё ещё использует его; для нового проекта используйте `SUPABASE_SECRET_KEY`. Не размещайте ключ и пароль в чате, браузере, Git или архиве.
5. На сервере скопируйте `.env.example` в `.env` и заполните `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `SUPABASE_STORAGE_BUCKET`. Сгенерируйте отдельный `EVIDENCE_VAULT_SECRET` командой `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Значения из старого архива не используются.
6. В `APP_ALLOWED_HOSTS` укажите реальный домен приложения. `TRUST_PROXY_COUNT=1` задавайте только при одном доверенном обратном прокси, который завершает HTTPS. Прокси должен передавать `X-Forwarded-Proto` и `Host` и закрывать прямой доступ к приложению извне.

Команда `check-setup` проверяет соединение с PostgreSQL, доступ к bucket, его приватность и настройки размера/MIME. Она не меняет базу и не загружает файлы. Если ошибка относится к глобальному лимиту Storage, проверьте его в Dashboard вручную.

## Запуск в Docker

```bash
cp .env.example .env
# Заполните .env на сервере
docker compose build
docker compose run --rm web flask --app app check-setup
docker compose run --rm web flask --app app db upgrade
# Если старую SQLite-базу переносить не нужно:
docker compose run --rm -it web flask --app app bootstrap-admin
docker compose up -d
```

Если нужен перенос старой базы, после `db upgrade` выполните команду из раздела ниже **вместо** `bootstrap-admin`. Приложение слушает `127.0.0.1:8080` хоста; настройте HTTPS в своём обратном прокси. Проверка процесса: `GET /healthz`. Миграции применяются **до** запуска новой версии. `flask db upgrade` создаёт таблицы и закрывает прямой доступ к ним для `anon`, `authenticated` и `service_role` через Data API; доступ к таблицам выполняет сервер по PostgreSQL-соединению.

Для запуска вне Docker установите зависимости `pip install -r requirements.txt`, экспортируйте переменные окружения и выполните `flask --app app db upgrade`, затем `gunicorn --workers 2 --bind 127.0.0.1:8080 'app:create_app()'`. На Windows Gunicorn не работает: для production используйте Linux-контейнер/сервер.

## Перенос данных из старого архива

Старый архив содержит `instance/evidence_vault.db`, `instance/uploads/` и локальный секрет. Распакуйте его **только в защищённую папку**, доступную на время переноса. Мигрируйте схему новой базы командой `db upgrade`, но **не создавайте администратора** до импорта. Импорт проверяет размер и SHA-256 каждого исходного файла, переносит пользователей, дела, доказательства и журнал, сохраняет старые пароли/настройки TOTP и обновляет последовательности PostgreSQL. Он разрешён только при пустой целевой базе.

```bash
# Если в старой базе не было администратора, укажите существующий email:
docker compose run --rm -v /absolute/path/to/old/instance:/legacy:ro web \
  flask --app app import-legacy \
  --sqlite-file /legacy/evidence_vault.db \
  --uploads-dir /legacy/uploads \
  --admin-email existing-user@example.com
```

Если старой базы нет или она пуста, вместо импорта выполните `bootstrap-admin`. После переноса сравните количество дел/файлов, проверьте скачивание и SHA-256 через интерфейс. Затем безопасно удалите временную копию старого архива с сервера. Старый Flask secret не переносится, поэтому прежние сеансы завершатся.

## Технические меры

- Сессия создаётся после пароля или разрешённого Google-аккаунта и TOTP; роль и активность читаются из базы на каждом запросе к защищённым страницам и действиям. Публичные стили, скрипты и значок сайта не обращаются к базе. Смена роли, блокировка, смена пароля и выход отзывают прежние сеансы. Кнопка «Выйти» завершает все сеансы пользователя, включая другие устройства и сохранённые копии cookie.
- TOTP-код нельзя повторно использовать, в том числе при одновременной первичной настройке 2FA. После пяти неудач действует блокировка на пять минут. Общий счётчик ошибок применяется к входу, смене пароля и подключению/отключению Google; чувствительные подтверждения во время блокировки возвращают 429. На форме включена CSRF-проверка.
- Частный Storage bucket доступен только серверу: до 20 файлов, 16 МБ каждый и 64 МБ за запрос. Перед отметкой об успешной загрузке сервер читает объект обратно и сравнивает SHA-256. Если часть файлов не сохранена, интерфейс показывает результат и имена неудачных файлов; сохранённые файлы остаются в деле. При неопределённом результате записи в базу файл не удаляется до подтверждения отсутствия метаданных.
- Карточка и сводка используют результат последнего наблюдения целостности, включая блокировку скачивания и проверку аудитором. Результат и время ручной проверки остаются отдельными полями; аудитор не изменяет их. Для старых записей без проверки показывается «Хеш рассчитан · требуется проверка».
- Отсутствующие объекты распознаются по HTTP 404 и по ответу Supabase HTTP 400 с `statusCode=404`, `error=not_found`. Другие ошибки 400 остаются ошибками сервиса. Скачивание изменённого или слишком большого объекта блокируется с 409.
- Сетевое ожидание Storage ограничено 30 секундами. Для пакета загрузки используется общий бюджет 90 секунд, для скачивания/проверки — 60 секунд; бюджет проверяется перед запросами и при чтении потока. Тайм-аут Gunicorn увеличен до 180 секунд для завершения обработки ошибки и очистки. Внешний HTTPS-прокси следует настроить с согласованным тайм-аутом.
- TLS, Secure/HttpOnly/SameSite cookie, ограничение Host, CSP и защитные заголовки настроены на сервере. Режим отладки выключен; Gunicorn заменяет встроенный сервер Flask.
- Таблицы создаются версионированной миграцией Alembic. Секреты передаются через переменные окружения.

Для реального ввода в эксплуатацию настройте резервное копирование **и PostgreSQL, и файлов Storage**, контроль доступа к Supabase Dashboard, мониторинг ошибок, внешний лимит запросов на вход/2FA, сканирование поступающих файлов при необходимости и политику хранения доказательств. Журнал действий находится в той же базе и не является независимым неизменяемым журналом.

## Проверка

### Скорость страниц

Статические ресурсы имеют версию по содержимому и сохраняются в браузере; изменение файла меняет его адрес. HTML и материалы дел сохраняют `Cache-Control: no-store`. Статистика обзора объединена в один запрос, а сотрудники, ответственные и авторы событий загружаются вместе с основными записями. Сводка использует снимок данных для отображения после сохранения события открытия, поэтому количество запросов не растёт с каждой строкой истории.

В PostgreSQL только явно перечисленные GET-страницы без записи используют AUTOCOMMIT, чтобы избежать лишних сетевых запросов BEGIN/ROLLBACK. Проверка пользователя остаётся свежей. POST-действия, скачивание, отчёты и экспорт сохраняют обычные транзакции. Для изолированных интеграционных проверок с `SET LOCAL search_path` настройка приложения `READ_PAGE_AUTOCOMMIT` выключается, чтобы сохранить границы временной схемы.

### Автоматические проверки

```bash
python -m unittest discover -s tests -v
```

Запускайте тесты этой командой из корня проекта, в том числе в терминале VS Code на Windows. Кнопка **Run Python File** запускает отдельный файл из папки `tests` и не добавляет корень проекта в путь импорта. Автотесты используют временную SQLite, имитацию Storage и подмену ответа Google; они проверяют права, 2FA, CSRF, SHA-256, загрузку, приглашение через Google, смену пароля и привязку Google. Они не выполняют вход в реальный Google-аккаунт. Перед использованием с настоящими данными выполните отдельную проверку на собственном проекте: миграция, регистрация приглашённого сотрудника, вход через Google, смена пароля, загрузка, скачивание, права трёх ролей и восстановление из резервной копии.
