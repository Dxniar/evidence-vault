## Задание и связь с проектом

Изучить способы двухфакторной аутентификации и написать программу, в которой первый фактор — многоразовый пароль, а второй выбирает студент. В Evidence Vault выбран второй фактор TOTP: шестизначный одноразовый код приложения-аутентификатора. Механизм защищает доступ к делам и цифровым материалам следователя.

Идентификатор локального пользователя — адрес электронной почты. При входе приложение проверяет пароль, затем TOTP. Успешный пароль создаёт только предварительный сеанс `preauth_user_id`; защищённые страницы остаются закрытыми. Полный сеанс `user_id` появляется после подтверждения второго фактора. Права следователя, аудитора и администратора проверяются отдельно после аутентификации.

## Принцип реализации

Пароль — фактор знания, а секрет в приложении-аутентификаторе — фактор владения. TOTP вычисляет код из общего секрета и временного счётчика. В проекте используется PyOTP, шаг 30 секунд и окно проверки текущего, предыдущего и следующего шага. Принятый шаг сохраняется в `last_totp_step`, поэтому повторная отправка того же кода после успешного входа отклоняется. Такой запрет повторного использования соответствует требованию раздела 5.2 [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238).

Пользователи создаются администратором; публичная регистрация отключена. При создании учётной записи `generate_password_hash()` сохраняет соль и результат парольного преобразования, а не открытый пароль. Сравнение выполняет `check_password_hash()`. Применяется механизм библиотеки Werkzeug; её текущий метод по умолчанию — scrypt. [Документация Werkzeug](https://werkzeug.palletsprojects.com/en/stable/utils/#werkzeug.security.generate_password_hash).

После пяти неудачных попыток учётная запись блокируется на 300 секунд. Выход повышает `session_version`, поэтому сохранённая старая cookie не восстанавливает доступ. Отдельно проверяются CSRF-токен, активность пользователя и версия сеанса. Секрет TOTP в действующей модели доступен серверу в восстанавливаемом виде; дополнительное шифрование этого поля и управляемое восстановление второго фактора остаются задачами усиления защиты.

## Листинги реализованных фрагментов

Приведены части действующего `app.py`, непосредственно реализующие лабораторную. Многоточия обозначают пропущенные ветви обработки, а не самостоятельную программу.

**Листинг 1. Проверка первого фактора и переход к предварительному сеансу (`login`).**

```python
elif (not user or not user.is_active or not user.has_local_password
      or not check_password_hash(user.password_hash, request.form.get("password", ""))):
    if user and user.is_active and user.has_local_password:
        fail_auth(user, "LOGIN_FAILED", "Неудачная попытка входа по паролю")
    flash("Неверная почта или пароль.", "danger")
else:
    session.clear()
    session["csrf_token"] = secrets.token_urlsafe(32)
    session["preauth_user_id"] = user.id
    session["preauth_version"] = user.session_version
    return redirect(url_for("verify_2fa" if user.totp_enabled else "setup_2fa"))
```

**Листинг 2. Проверка формата кода и допустимого временного шага.**

```python
def matching_totp_step(secret: str, submitted: str) -> int | None:
    code = submitted.strip()
    if len(code) != 6 or not code.isascii() or not code.isdigit():
        return None
    current_step = int(utc_now().timestamp() // 30)
    totp = pyotp.TOTP(secret)
    for step in (current_step, current_step - 1, current_step + 1):
        if secrets.compare_digest(totp.at(step * 30), code):
            return step
    return None
```

**Листинг 3. Однократное принятие второго фактора (`verify_2fa`).**

```python
step = matching_totp_step(user.totp_secret, request.form.get("code", ""))
if step is not None:
    result = db.session.execute(update(User).where(User.id == user.id, User.is_active.is_(True),
        User.session_version == session["preauth_version"])
        .where((User.locked_until.is_(None)) | (User.locked_until <= utc_now()))
        .where((User.last_totp_step.is_(None)) | (User.last_totp_step < step))
        .values(last_totp_step=step, failed_attempts=0, locked_until=None, last_login=utc_now()))
    if result.rowcount == 1:
        if session.get("preauth_method") == "google":
            append_event("GOOGLE_LOGIN_SUCCESS", "Успешный вход через Google и TOTP", "success", user.id)
        else:
            append_event("LOGIN_SUCCESS", "Успешный вход с двухфакторной проверкой", "success", user.id)
        db.session.commit()
        start_session(user)
        return redirect(url_for("account" if user.must_change_password else "dashboard"))
```

Обновление содержит условия активности, блокировки, версии сеанса и ещё не использованного шага. Полный сеанс создаётся только при `rowcount == 1`. Первичная настройка в `setup_2fa` дополнительно требует `totp_enabled == False`, показывает QR-код с provisioning URI и включает второй фактор после подтверждения кода.

## Ответы на контрольные вопросы

**1. Перечислите наиболее распространённые способы реализации двухфакторной аутентификации.**

Распространены комбинации пароля с TOTP/HOTP из приложения или аппаратного токена; пароля с кодом через SMS либо отдельный канал; пароля с подтверждением push-запроса на зарегистрированном устройстве; пароля/PIN с криптографической смарт-картой или ключом. Биометрия может быть фактором активации аппаратного или программного аутентификатора. Два пароля либо пароль и секретный вопрос относятся к одной категории знания и сами по себе не создают два разных фактора.

**2. Перечислите достоинства и недостатки указанных способов.**

| Способ | Достоинства | Недостатки |
|---|---|---|
| TOTP в приложении | Не требует SMS и мобильной сети; доступен на распространённых телефонах | Нужна синхронизация времени; утрата или копирование секрета требует восстановления; вводимый код может быть похищен фишингом |
| HOTP или аппаратный OTP-токен | Отдельное устройство; возможна работа без сети | Стоимость и учёт устройства; у HOTP возможна рассинхронизация счётчика; вводимый код подвержен фишингу |
| SMS-код | Простое внедрение; понятен пользователю | Зависимость от оператора и доставки; риски переноса номера и перехвата; слабее криптографического устройства |
| Push-подтверждение | Удобный вход; приложение может показывать контекст запроса | Зависимость от сети; риск ошибочного подтверждения и множества навязанных запросов |
| Криптографический ключ/смарт-карта с PIN | Не передаёт секрет как введённый код; протокол с привязкой к проверяющей стороне может противостоять фишингу | Покупка и выдача устройств; требования совместимости; необходимость процедуры утраты и замены |
| Биометрическая активация устройства | Быстрый доступ без запоминания дополнительного кода | Ошибки распознавания, требования к сенсору и защите шаблона; биометрию сложно заменить после компрометации |

Обычная OTP-аутентификация не считается устойчивой к фишингу: злоумышленник способен передать вручную введённый код настоящему сервису. Биометрию следует рассматривать вместе с конкретным устройством и протоколом, а не как обещание безошибочного распознавания. [NIST SP 800-63B, разделы 3.1 и 3.2.5](https://pages.nist.gov/800-63-4/sp800-63b.html).
