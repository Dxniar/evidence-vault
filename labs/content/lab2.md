## Задание и связь с проектом

Изучить способы федеративной аутентификации и написать программу реализации такого механизма. В Evidence Vault используется Google OpenID Connect: Google выступает поставщиком идентификации, Evidence Vault — приложением, принимающим подтверждённую внешнюю личность. Пароль Google вводится на стороне Google и не передаётся в форму Evidence Vault.

Права на дела остаются в локальной базе проекта. Google-аккаунт должен быть заранее привязан к пользователю либо соответствовать действующему приглашению администратора. Внешняя аутентификация не выдаёт роль администратора и не разрешает произвольную саморегистрацию. При каждом запуске Google-входа приложение явно запрашивает выбор аккаунта. Для следователя после подтверждённого Google-входа отдельный локальный TOTP не требуется; для администратора и аудитора он обязателен. При входе по почте и паролю TOTP обязателен для всех ролей.

## Теоретическое основание

OpenID Connect добавляет идентификацию пользователя поверх OAuth 2.0. Приложение запрашивает области `openid email`, получает код авторизации и через серверный клиент принимает проверенные сведения ID Token. Поставщик публикует параметры через discovery-документ. В проекте настроен Authlib с `code_challenge_method="S256"`. [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html).

Для связи локальной записи с внешней личностью сохраняется `google_sub`. Google рекомендует идентифицировать аккаунт через `sub`, поскольку адрес электронной почты может меняться. В проекте email используется при контролируемой первой привязке и принятии приглашения, а последующий поиск выполняется по `google_sub`. [Документация Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).

Федеративная аутентификация и локальная авторизация разделены: внешняя сторона подтверждает личность, а Evidence Vault применяет роль, активность, блокировку и права на конкретное дело. Учетная запись может быть отключена локально независимо от наличия действующего Google-аккаунта.

## Листинги реализованных фрагментов

Приведены относящиеся к заданию части действующего `app.py`. Authlib реализует обмен протокола и проверку OIDC-токена; прикладные правила проверяются Evidence Vault.

**Листинг 1. Подключение поставщика идентификации (`create_app`).**

```python
oauth = OAuth(app)
app.extensions["evidence_google_oauth"] = oauth.register(
    "google", client_id=app.config["GOOGLE_OAUTH_CLIENT_ID"],
    client_secret=app.config["GOOGLE_OAUTH_CLIENT_SECRET"],
    server_metadata_url="https://accounts.google.com/.well-known/openid-configuration",
    client_kwargs={"scope": "openid email", "code_challenge_method": "S256"})
```

Ключи задаются в конфигурации среды и не встраиваются в отчёт. При отсутствии конфигурации функция входа скрыта и маршрут возвращает 404.

**Листинг 2. Запуск федеративного входа (`google_login`, успешная ветвь).**

```python
session.clear()
session["google_flow"] = "login"
try:
    return client.authorize_redirect(
        url_for("google_callback", _external=True), prompt="select_account")
except (OAuthError, RequestException, ValueError) as exc:
    app.logger.warning("Google sign-in could not start: %s", type(exc).__name__)
    clear_google_flow()
    flash("Google сейчас недоступен. Попробуйте позже.", "danger")
    return redirect(url_for("login"))
```

**Листинг 3. Приём и проверка обязательных сведений (`google_callback`).**

```python
token = client.authorize_access_token()
claims = token.get("userinfo")
sub = claims.get("sub") if claims else None
email = claims.get("email") if claims else None
if (not isinstance(sub, str) or not 1 <= len(sub) <= 255 or not sub.isascii()
        or not isinstance(email, str) or not email.strip()
        or (claims.get("email_verified") is not True
            and claims.get("email_verified") != "true")):
    clear_google_flow()
    flash("Google не подтвердил данные аккаунта. Вход отклонён.", "danger")
    return redirect(url_for("account" if g.user else "login"))
```

В действующей функции обмен обёрнут обработкой ошибок OAuth, сети и токена. До обмена проверяется, что в сеансе существует ожидаемый поток `login` или `link`. Authlib выполняет проверку `state` и подписанного ID Token. Отдельный тест с настоящим клиентом Authlib отклоняет callback с незапрошенным `state` без сетевого обмена.

Параметр `prompt="select_account"` передаётся также при подключении Google к профилю. Он запрашивает экран выбора аккаунта при каждой новой попытке входа; повторный ввод пароля Google определяется самим провайдером.

**Листинг 4. Выбор процедуры входа по локальной роли.**

```python
user = db.session.scalar(select(User).where(User.google_sub == sub))
# При отсутствии привязки выше по потоку проверяется приглашение администратора.
# Недоступный пользователь получает GOOGLE_LOGIN_DENIED и перенаправление.
if user.role == "investigator":
    user.last_login = utc_now()
    user.failed_attempts = 0
    user.locked_until = None
    append_event("GOOGLE_LOGIN_SUCCESS", "Успешный вход через Google", "success", user.id,
                 details={"auth_method": "google", "local_totp_required": False})
    db.session.commit()
    start_session(user, auth_method="google")
    return redirect(url_for("account" if user.must_change_password else "dashboard"))
session.clear()
session["csrf_token"] = secrets.token_urlsafe(32)
session["preauth_user_id"] = user.id
session["preauth_version"] = user.session_version
session["preauth_method"] = "google"
return redirect(url_for("verify_2fa" if user.totp_enabled else "setup_2fa"))
```

Комментарии в последнем листинге поясняют опущенную ветвь. До выбора процедуры действующий код отклоняет отсутствующую, отключённую или заблокированную учётную запись; совпадение email само по себе не привязывает существующий локальный аккаунт. Сеанс без локального TOTP допускается только для следователя: сервер проверяет способ входа, совпадение `google_sub`, активность, роль и версию сеанса. Обычная проверка признака `totp_enabled` сама по себе не заменяет эти условия.

## Реальный порядок работы программы

1. Администратор создаёт локального пользователя с ролью либо приглашение на точный email. Другой путь — авторизованный пользователь подключает Google в своём профиле, подтвердив локальный пароль. Для привязки требуется совпадение подтверждённого email, а один `sub` не может принадлежать двум пользователям.
2. Пользователь выбирает «Войти через Google». CSRF-защищённый POST запускает переход к поставщику с `prompt=select_account`.
3. Пользователь выбирает аккаунт и проходит требуемые Google проверки. После возвращения серверный клиент обрабатывает callback и подтверждённые сведения личности.
4. Evidence Vault ищет привязку по `sub` либо принимает активное неистёкшее приглашение без локального пароля. Приглашение предварительно содержит роль и действует семь дней. Обычное совпадение email с существующим локальным пользователем не разрешает вход.
5. Следователь получает полный сеанс Google без отдельного локального TOTP. Администратор и аудитор получают предварительный сеанс и подтверждают TOTP либо сначала настраивают его; до этого защищённые страницы для них закрыты.
6. При завершении выбранной процедуры создаётся событие `GOOGLE_LOGIN_SUCCESS`. Права определяются локальной ролью. Отключение пользователя, изменение роли и отзыв версии сеанса закрывают доступ. Отвязка Google также завершает сеанс следователя, созданный только через Google.
7. Следователь, вошедший только через Google, может дополнительно подключить TOTP в профиле и создать локальный пароль. Это нужно для резервного входа по паролю; при таком входе TOTP остаётся обязательным.

## Фактически выполненная проверка

14 октября 2026 года выполнен реальный вход администратора на опубликованном сайте Evidence Vault: после Google открыт экран TOTP, владелец самостоятельно ввёл код и подтвердил открытие страницы «Обзор». Исправлено несовпадение callback из-за лишней точки в разрешённом URI. Результат и ссылки на снимки сохранены в `output/deploy/deployment.json`; секреты и коды в отчёт не включены. Эта проверка относится к ветви администратора с TOTP и не подтверждает новую ветвь следователя без локального TOTP или поведение выбора аккаунта после последующих изменений.

Для воспроизводимой проверки прикладных правил используется `FakeGoogle`: он заменяет только переход и полученные сведения личности. Маршруты Evidence Vault, база учётных записей, TOTP, права и журнал работают в штатном коде. Такая проверка не подтверждает подпись реального Google ID Token, обмен с Google, доступность интернета или настройки OAuth Console. Она подтверждает реакцию проекта на контролируемые входные данные. Отдельные тесты строят настоящий URL авторизации через Authlib и проверяют `prompt=select_account`, `state`, `nonce` и PKCE без обращения к сети.

`labs/verify_auth.py` использует SQLite в памяти, MemoryStorage и синтетические аккаунты. Запуск выполнен в отдельном контейнере без сети; рабочая Supabase и реальные пользователи не используются. В JSON явно записаны `real_google_sign_in_performed: false` и `federation_transport: FakeGoogle (synthetic claims)`.

Актуальный набор проверяет следующие сценарии:

| Сценарий | Фактический результат |
|---|---|
| Известный `sub` следователя, подтверждённый email | Обзор доступен после Google без отдельного локального TOTP |
| Известный `sub` администратора или аудитора | Переход к TOTP; до его подтверждения обзор закрыт |
| Вход следователя по почте и паролю | TOTP обязателен, независимо от разрешённого Google-входа |
| Повторный запуск Google-входа после выхода | Новый запрос содержит `prompt=select_account`, новые `state`, `nonce` и PKCE |
| Правильный TOTP после Google для привилегированных ролей | Обзор открыт; зарегистрирован `GOOGLE_LOGIN_SUCCESS` |
| Роль внешне вошедшего аудитора | Создание дела и управление сотрудниками возвращают 403 |
| Совпадающий email без привязки | Вход отклонён; автоматическая привязка не создана |
| Неподтверждённый email | Callback отклонён |
| Callback без ожидаемого потока | Возврат к входу |
| Отключённый локальный пользователь | Вход отклонён независимо от внешнего `sub` |
| Изменение роли, отключение или отвязка Google | Ранее выданный сеанс следователя без локального TOTP больше не даёт доступа |

## Вывод

Механизм федеративной идентификации реализован непосредственно в Evidence Vault через Google OpenID Connect. Внешняя личность получает только заранее назначенные локальные права. Следователь входит через Google без отдельного локального TOTP; администратор и аудитор подтверждают TOTP, а при входе по паролю он обязателен для всех. Каждый новый Google-запрос явно запрашивает выбор аккаунта. Реальный вход администратора с TOTP подтверждён отдельно от изолированных тестов; для новой ветви следователя требуется самостоятельная сквозная демонстрация с действующим Google-провайдером.
