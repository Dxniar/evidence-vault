## Название и цель

**Тема:** основные принципы протоколирования работы приложения.

**Цель:** изучить механизмы и конфигурацию протоколирования; реализовать подпрограмму журналирования событий прикладной программы.

Работа выполнена на примере Evidence Vault — системы учёта дел, файлов доказательств и действий сотрудников. Язык реализации — Python, прикладной сервер — Flask, рабочая база — PostgreSQL в Supabase. Проверки лабораторной используют отдельную SQLite в памяти и MemoryStorage; настоящие материалы дел не изменяются.

## Реализация в проекте

Проект использует два журнала с разными задачами.

| Журнал | Назначение и данные | Хранение и конфигурация |
|---|---|---|
| Прикладной аудит | Кто выполнил действие, тип события, результат, IP, время UTC, дело и файл, структурированные сведения | Таблица `audit_logs`; доступ через страницу «Журнал» по роли и доступным делам. Успешное действие и его событие сохраняются одной транзакцией |
| Эксплуатационные сообщения | Недоступность базы или Storage, ошибки Google OAuth, незавершённая загрузка, проверка готовности | Стандартный модуль `logging`; одна JSON-запись на строку в потоке контейнера. Уровень задаётся `APP_LOG_LEVEL`; объём Docker-журнала ограничивается ротацией |

В Python `Logger` определяет уровень сообщения, `Handler` задаёт назначение, `Formatter` — представление. Порог уровня исключает сообщения меньшей важности. Это стандартные механизмы Python, которые используются в модуле `audit_logging.py`. [Документация Python 3.12](https://docs.python.org/3.12/library/logging.html).

Эксплуатационный журнал содержит `timestamp`, `level`, `logger`, `message`, а в HTTP-контексте — случайный `request_id`. Идентификатор совпадает с заголовком ответа `X-Request-ID`; он помогает найти сообщение об ошибке без публикации содержимого запроса. При записи исключения сохраняется его класс, но не текст исключения и не трассировка. Форматтер не переносит в журнал заголовки, параметры запроса и произвольные поля `extra`. Общие формы паролей, токенов и URL заменяются метками. Такая маскировка служит дополнительной защитой: разработчик всё равно не должен передавать в журнал секреты, содержимое доказательств или параметры SQL.

Конфигурация проекта: `APP_LOG_LEVEL=INFO`; допустимы `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`. Диагностика направляется в поток, собираемый Docker. Для `json-file` используются `max-size: "10m"` и `max-file: "3"`. Эти ограничения относятся к эксплуатационным сообщениям контейнера; они не очищают таблицу прикладного аудита. Параметр `max-file` ограничивает число файлов при заданном `max-size`. [Документация Docker](https://docs.docker.com/engine/logging/drivers/json-file/).

## Листинг подпрограммы журналирования

Ниже приведена реальная функция из `app.py`. Она формирует объект класса `AuditLog` и добавляет его в текущую транзакцию. Отдельного `commit()` внутри функции нет: вызывающее действие завершает транзакцию после сохранения своих изменений.

```python
def append_event(event_type: str, description: str, severity: str = "info", user_id: int | None = None,
                 *, case_id: int | None = None, evidence_id: int | None = None, details: dict | None = None):
    actor_id = user_id if user_id is not None else (g.user.id if g.user else None)
    actor = db.session.get(User, actor_id) if actor_id is not None else None
    db.session.add(AuditLog(user_id=actor_id,
                            event_type=event_type, description=description, severity=severity,
                            actor_name=actor.name if actor else None, actor_email=actor.email if actor else None,
                            case_id=case_id, evidence_id=evidence_id,
                            details_json=json.dumps(details, ensure_ascii=False, sort_keys=True) if details else None,
                            ip_address=request.remote_addr or "—"))
```

Время `created_at` задаётся моделью через `utc_now`. Поля `actor_name` и `actor_email` сохраняют снимок автора: последующее переименование пользователя не меняет отображаемый авторский снимок. ORM запрещает изменение и удаление сохранённого `AuditLog`; в PostgreSQL дополнительно действуют триггеры. Администратор базы с достаточными привилегиями может отключить защиту, поэтому этот механизм не равнозначен независимому неизменяемому архиву.

Для ошибок введена следующая реальная функция конфигурации из `audit_logging.py`. Класс `SafeJsonFormatter` в том же модуле задаёт UTC, ограничение сообщения 2048 символами, маскировку и перечень допустимых полей.

```python
def configure_application_logging(app: Flask, *, stream: TextIO | None = None) -> None:
    name = str(app.config.get("APP_LOG_LEVEL", "INFO")).strip().upper()
    if name not in LOG_LEVELS:
        raise ValueError("APP_LOG_LEVEL: ожидается DEBUG, INFO, WARNING, ERROR или CRITICAL.")
    logger = app.logger
    for old in tuple(logger.handlers):
        logger.removeHandler(old)
        if getattr(old, "_evidence_managed", False):
            old.close()
    handler = logging.StreamHandler(stream)
    handler._evidence_managed = True
    handler.setFormatter(SafeJsonFormatter())
    logger.addHandler(handler)
    logger.setLevel(LOG_LEVELS[name])
    logger.propagate = False
```

## Дополнение: экспорт и резервное копирование журнала

В обновлённом проекте реализованы `audit_archive.py` и `audit_restore.py`. Администратор и аудитор экспортируют журнал в CSV с текущими фильтрами, независимо от пагинации. Следователь получает отказ сервера при попытке экспорта. CSV содержит русские заголовки, UTF-8 BOM, разделитель `;` и нейтрализацию потенциальных формул.

Администратор вручную создаёт полный ZIP журнала в приватном Storage. Архив включает `journal.jsonl` с исходными полями и `manifest.json` с версией, границей ID, числом событий и SHA-256. Сервер проверяет чтение после записи; каталог копий хранится в неизменяемых событиях `AUDIT_BACKUP_CREATED`. Экспорт, создание, выдача и восстановление фиксируются событиями `AUDIT_EXPORTED`, `AUDIT_BACKUP_CREATED`, `AUDIT_BACKUP_DOWNLOADED`, `AUDIT_BACKUP_RESTORED`.

Копия проверяется без подключения к БД командой `python audit_restore.py --file backup.zip`. Восстановление доступно только административной CLI-командой в пустую `audit_logs`, при наличии исходных связанных пользователей, дел и доказательств. Вставки исходных ID/дат, событие восстановления и изменение последовательности PostgreSQL выполняются одной транзакцией. Существующий журнал не очищается и не перезаписывается.

Проверены 160 тестов общего набора в Docker без сети, включая 22 сценария архива и экспорта и 10 сценариев восстановления. Дополнительно на отдельном PostgreSQL 16 выполнены 14 проверок восстановления: сохранение данных, внешние ключи, последовательность ID, отказ для непустого журнала и полный откат после поздней ошибки. Рабочая Supabase не использовалась; временные контейнеры и сеть удалены. Исторический результат 11 тестов и каталог 35 типов выше относится к первоначальной проверке, а не к полному текущему набору.

На демонстрации нужно показать отсутствие кнопок у следователя, CSV у аудитора, создание и скачивание ZIP администратором и успешную автономную проверку скачанного файла. SHA-256 выявляет повреждение, но не удостоверяет автора архива; для независимой копии архив сохраняют вне основной инфраструктуры.
