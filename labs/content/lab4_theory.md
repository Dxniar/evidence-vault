# Лабораторная работа № 4. Реализация политики безопасности в MS Windows

Цель: освоить средства администрирования и аудита Windows на компьютере, с которого разрабатывается и используется Evidence Vault.

## Связь с проектом

Объект лабораторной — Windows на рабочей станции следователя и администратора. На этом компьютере запускаются браузер и Docker Desktop, через которые используется Evidence Vault; сервер Flask работает в Linux-контейнере, а PostgreSQL и файловое хранилище размещены в Supabase. Компрометация Windows может позволить прочитать локальную конфигурацию проекта, перехватить сеанс браузера или получить административный доступ к Docker. Поэтому защита приложения дополняется защитой рабочей станции.

Журнал Windows Security описывает вход в Windows, действия с системными учетными записями, привилегиями и политиками. Журнал Evidence Vault описывает вход в приложение, операции с делами, файлами, участниками и ответственностью. В проекте предусмотрены роли администратора, следователя и аудитора, проверка TOTP и учет событий аутентификации. Учетная запись приложения не становится учетной записью Windows; запись входа в Evidence Vault не доказывает наличие события Windows 4624. Аналогично Linux-контейнер не заменяет локальную политику Windows, а права приложения не являются Software Restriction Policies (SRP).

## Параметры задания и соответствие реестру

Четыре первых параметра находятся в `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System`, пятый — в `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon`. Соответствие имен параметрам приведено в документации Microsoft по [Windows security baseline](https://learn.microsoft.com/en-us/azure/governance/policy/samples/guest-configuration-baseline-windows); серверные рекомендации этой страницы не переносились на клиентскую ОС целиком.

| Параметр задания | Имя значения | Тип и требуемое значение |
|---|---|---|
| Заголовок сообщения при входе | `legalnoticecaption` | REG_SZ: `ПРЕДУПРЕЖДЕНИЕ` |
| Текст сообщения при входе | `legalnoticetext` | REG_SZ: `На этом компьютере могут работать только зарегистрированные пользователи!` |
| Не требовать CTRL+ALT+DEL — отключено | `DisableCAD` | REG_DWORD: `0` |
| Не отображать имя последнего пользователя — включено | `DontDisplayLastUserName` | REG_DWORD: `1` |
| Предупреждать об истечении пароля за 7 дней | `PasswordExpiryWarning` | REG_DWORD: `7` |

Значение `DisableCAD=0` означает требование защищенной последовательности клавиш, а не отключение CTRL+ALT+DEL. Настройка предупреждения за семь дней сама по себе не устанавливает срок действия пароля. Фактическое предупреждение зависит от того, истекает ли пароль конкретной учетной записи; наличие значения в реестре не означает, что диалог уже появился. См. [политику предупреждения об истечении пароля](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/interactive-logon-prompt-user-to-change-password-before-expiration).

## Категории аудита

Для каждой из пяти категорий задания требуется аудит успехов и отказов. GUID позволяют выбирать категории независимо от языка интерфейса Windows. Два пункта задания о входе соответствуют разным категориям: вход/выход на целевом компьютере и проверка учетных данных. На компьютере без домена события Kerberos контроллера домена ожидать не следует. См. [константы аудита Microsoft](https://learn.microsoft.com/en-us/windows/win32/secauthz/auditing-constants).

| Категория | GUID |
|---|---|
| Вход/выход (Logon/Logoff) | `{69979849-797A-11D9-BED3-505054503030}` |
| Вход учетной записи (Account Logon) | `{69979850-797A-11D9-BED3-505054503030}` |
| Изменение политики (Policy Change) | `{6997984D-797A-11D9-BED3-505054503030}` |
| Использование привилегий (Privilege Use) | `{6997984B-797A-11D9-BED3-505054503030}` |
| Управление учетными записями (Account Management) | `{6997984E-797A-11D9-BED3-505054503030}` |

Применение категории через `auditpol /set /category:<GUID> /success:enable /failure:enable` включает соответствующие подкатегории системного аудита. Проверяется действующее состояние, а не только выбранное значение интерфейса: `auditpol /get /category:<GUID>`. См. [auditpol set](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/auditpol-set).

На современных Windows расширенный аудит и старые настройки категорий могут конфликтовать. Дополнительное значение `SCENoApplyLegacyAuditPolicy=1` в `HKLM\SYSTEM\CurrentControlSet\Control\Lsa` запрещает применение старых категорий; его необходимо учитывать отдельно, сохранять перед изменением и восстанавливать при откате. Оно не входит в пять параметров интерактивного входа. См. [Event Audit Policies](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-gpsb/506f97dd-00f9-49dc-b3ba-bb041328cafb).

## Журнал событий безопасности и дополнительные параметры

Место хранения конкретного журнала определяется его конфигурацией, которую показывает `wevtutil gl Security`. Обычный путь — `%SystemRoot%\System32\winevt\Logs\Security.evtx`; его следует подтвердить выводом на этом компьютере. Доступные параметры: максимальный размер, режим хранения и автоматическое архивирование. При `retention=false` новые события замещают самые старые; при `retention=true` старые сохраняются и новые могут отбрасываться после заполнения. Автоархивирование требует `retention=true`. Минимальный размер — 1 МБ, размер округляется до кратного 64 КБ. Задание требует исследовать свойства; изменение размера и очистка журнала не обязательны. См. [wevtutil](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/wevtutil).

В параметрах безопасности дополнительно рассматриваются приоритет подкатегорий аудита, аудит использования привилегий резервного копирования и восстановления, аудит глобальных системных объектов, принудительное создание аудита и остановка системы при невозможности записи аудита. Для учебной работы не требуется включать аварийную остановку или очищать Security. Увеличение объема аудита требует контроля заполнения и хранения. См. [настройку аудита Microsoft](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/plan/security-best-practices/monitoring-active-directory-for-signs-of-compromise).

Для нескольких реально найденных событий в отчет включаются полный текст и XML: дата и время, источник, Event ID, Record ID, компьютер, субъект и остальные поля события. Типовые события: 4624 — успешный вход, [4625 — отказ входа](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4625), [4672 — специальные привилегии нового входа](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4672), [4719 — изменение политики аудита](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4719). Это примеры для поиска, а не утверждение, что они обнаружены на данной машине. Не следует специально создавать ошибочные входы, блокировать учетные записи или очищать журнал ради иллюстрации.

## Ограниченное использование программ

Для просмотра SRP нужны разделы «Уровни безопасности» и «Дополнительные правила» оснастки локальной политики. Основные уровни — «Запрещено» (Disallowed) и «Неограниченный» (Unrestricted). Последний сохраняет права текущего пользователя и не выдает права администратора. Уровень «Обычный пользователь» встречается в старых материалах; его наличие и работоспособность на Windows 11 не предполагаются. См. [SRP Technical Overview](https://learn.microsoft.com/en-us/windows-server/identity/software-restriction-policies/software-restriction-policies-technical-overview).

Дополнительные правила идентифицируют программу по хешу, пути, сертификату или интернет-зоне. Хеш привязан к содержимому файла; путь — к месту размещения; сертификат — к подписи. Правила интернет-зоны из старой реализации ограничены пакетами Windows Installer и не означают универсальную блокировку всех файлов, скачанных браузером. См. [SRP Tools and Settings](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2003/cc782454(v=ws.10)) и [SRP Rules](https://learn.microsoft.com/en-us/windows-server/identity/software-restriction-policies/work-with-software-restriction-policies-rules).

SRP считается устаревшей технологией начиная с Windows 10 build 1803; для нового промышленного контроля запуска Microsoft указывает App Control for Business/WDAC или AppLocker. В этой лабораторной изучается именно SRP из задания. См. [состояние SRP](https://learn.microsoft.com/en-us/windows-server/identity/software-restriction-policies/software-restriction-policies).

## Ответы на контрольные вопросы

### 1. Какие события безопасности должны фиксироваться в журнале аудита?

Успешные и неудачные попытки аутентификации, выход и отзыв сеансов, создание и изменение учетных записей, выдача и использование значимых привилегий, изменение политики, обращения к защищенным объектам, отказ доступа, остановка защиты и очистка журнала. В Evidence Vault дополнительно фиксируются создание и изменение дел, загрузка и выдача файлов, результаты проверки целостности, изменение участников, закрытие дела и передача ответственности. Для расследования нужны субъект, время, объект, действие и результат; пароли, коды TOTP и секретные ключи в журнал не записываются.

### 2. Какие параметры определяют политику аудита?

Выбранные категории и подкатегории, аудит успеха и отказа, область применения к системе или пользователям, правила SACL для доступа к объектам, приоритет расширенной политики, а также права просмотра и управления журналом. Политика хранения задает объем журнала, поведение при заполнении, архивирование и срок сохранения. В Evidence Vault категории выражены действиями приложения и результатом операции; для их связи с Windows нужна синхронизация времени и сопоставление источников, поскольку это два разных журнала.

### 3. Целесообразно ли объединять функции администратора и аудитора?

Для системы с материалами дел их следует разделять. Администратор изменяет настройки и права, аудитор проверяет действия и выявляет нарушения. Совмещение позволяет одному человеку и выполнить изменение, и скрыть его последствия. Разные роли Evidence Vault поддерживают это разделение на уровне приложения, но привилегированный администратор базы или хранилища остается отдельной угрозой: одних ролей интерфейса недостаточно для независимого аудита.

### 4. Целесообразно ли разрешать анонимный доступ к информационным ресурсам?

К материалам расследований, персональным данным, журналу и административным функциям — нет. Без установленного субъекта нельзя применять индивидуальные права и определить ответственность за действие. Публичными могут оставаться только намеренно открытые ресурсы, например форма входа и общедоступная справка, с минимальным раскрытием состояния системы. В Evidence Vault просмотр дел должен требовать аутентификации и проверки области доступа.

### 5. Как должен передаваться пароль или другая аутентифицирующая информация?

Через аутентифицированный шифрованный канал с проверкой сертификата сервера, для веб-приложения — HTTPS/TLS. Пароли и токены нельзя помещать в адрес страницы, обычные логи, сообщения чата или незашифрованные файлы обмена. На сервере пароли хранятся в виде устойчивых к перебору хешей; MFA и защита сеанса дополняют транспорт. Локальный учебный HTTP на loopback не является подтверждением безопасного сетевого развертывания Evidence Vault.

### 6. Нужно ли ограничивать запуск прикладных программ и почему?

Да, особенно на рабочем месте с доказательствами. Непроверенное ПО может читать выгруженные материалы, красть токены и изменять файлы. Контроль должен разрешать необходимые подписанные браузер, системные средства и утвержденные служебные приложения; рабочую станцию разработчика с Docker следует учитывать отдельно. Ограничения сначала проверяются на тестовом компьютере, чтобы не остановить работу. Ролевые права Evidence Vault ограничивают действия в приложении и не ограничивают запуск программ Windows.

### 7. Какое дополнительное правило наиболее эффективно и почему?

Для небольшого стабильного набора конкретных служебных программ удобно правило хеша: перенос или переименование файла не снимает привязку к содержимому, а изменение файла меняет хеш. Недостаток — правило нужно обновлять после штатного обновления программы. В большой организации практичнее проверенные правила издателя/подписи современной системы контроля приложений. Правила пути без контроля прав записи в разрешенную папку слабее. Хеш доказательства в Evidence Vault проверяет целостность материала и не является SRP-правилом запуска программы.

### 8. Из каких этапов состоит построение политики безопасности?

Инвентаризация ресурсов и пользователей; определение угроз и требований; распределение ролей и ответственности; выбор правил доступа, аутентификации, запуска ПО, аудита и хранения; подготовка восстановления и отката; проверка на стенде; поэтапное применение; сбор подтверждений; мониторинг и регулярный пересмотр. Для Evidence Vault отдельно описываются рабочая станция Windows, контейнер приложения и облачные база/хранилище, потому что у них разные средства защиты и администраторы.

### 9. К чему приводит ошибочное определение политики безопасности?

Слишком широкие права позволяют читать чужие дела или менять настройки; отсутствие отказов в журнале скрывает перебор паролей; слишком маленький журнал вытесняет нужные события. Неверный запрет запуска может заблокировать браузер, Docker или средства восстановления. Включение остановки при невозможности записи аудита без контроля заполнения способно вывести рабочую станцию из эксплуатации. Поэтому до применения нужны резервная копия параметров, проверка действующего состояния и план отката.

### 10. Почему администраторы пренебрегают многими параметрами?

Причины — незнание механизмов, нехватка времени, страх остановить рабочие процессы, несовместимость со старым ПО, шум в журнале и отсутствие ответственного за анализ событий. Дополнительно мешают различия редакций Windows и конфликт старых и расширенных политик. Решение — документированная базовая конфигурация, автоматическая проверка, безопасный откат и контроль существенных событий. В Evidence Vault учебные проверки полезны только при честном указании реально примененных настроек и оставшихся ограничений.

## Что наблюдалось и что нужно подтвердить

Срез ниже выполнен только чтением до применения настроек. Из него нельзя делать вывод о конечном состоянии после работы другого процесса.

| Объект | Наблюдение на этом компьютере | Требуемое подтверждение для отчета |
|---|---|---|
| Редакция Windows | `EditionID=Core`, 24H2, build 26100; это Windows 11 Home. Реестровая строка ProductName сохраняет старую метку Windows 10 Home | Сведения о системе с редакцией и сборкой |
| Оснастка политики | `C:\Windows\System32\secpol.msc` отсутствует | Нельзя объявлять окна secpol открытыми; зафиксировать ограничение Home |
| Заголовок/текст | Заголовок пуст, текст содержит нулевой символ | Сохраненные значения до/после; фактический экран входа требует отдельного просмотра без принудительного выхода из текущего сеанса |
| CTRL+ALT+DEL | Значение `DisableCAD` отсутствует | После применения подтвердить `0`; отсутствие исходного значения не приравнивать к явно установленному `0` |
| Имя последнего пользователя | `DontDisplayLastUserName=0` | После применения подтвердить `1`; вид экрана входа отдельно |
| Срок предупреждения | `PasswordExpiryWarning=5` | После применения подтвердить `7`; изменение срока пароля не требуется |
| Приоритет расширенного аудита | В правильной ветви `Control\Lsa` значение `SCENoApplyLegacyAuditPolicy` отсутствует | Если менялось, сохранить и проверить отдельно |
| Категории аудита и свойства Security | Чтение в ограниченном процессе вернуло Access denied | Чтение с нужными правами, сохраненный вывод действующих категорий и конфигурации журнала |
| События Windows | В рамках этого исследования не экспортировались | Полные тексты и XML нескольких действительно обнаруженных событий |
| SRP | Ветка CodeIdentifiers есть, AuthenticodeEnabled=0; DefaultLevel, PolicyScope, TransparentEnabled и дочерние правила не обнаружены | Это не доказательство действующего SRP; снимки уровней и правил оснастки на Home пока недоступны |

Если преподаватель требует именно экранные формы SRP, понадобится поддерживаемая Windows Pro/Enterprise/Education в отдельной согласованной среде. Снимки интерфейса Evidence Vault, имитация окон в HTML или настройки Linux-контейнера не подтверждают выполнение этого пункта Windows. Использование другой среды должно быть явно обозначено в отчете.

## Вывод

Для Evidence Vault безопасность рабочей станции дополняет проверки доступа и целостности в приложении. Лабораторная охватывает предупреждение при входе, защищенную последовательность клавиш, сокрытие последнего пользователя, предупреждение об истечении пароля, пять категорий аудита и исследование SRP. Фактический результат применения и наличие экранных форм подтверждаются отдельными артефактами; на Windows Home нельзя считать отсутствующие оснастки выполненными только по аналогии с приложением.
